# Презентация: сервис бронирования переговорных коворкинга

Структура документа соответствует требованиям описания полного ЖЦ продукта. Каждый заголовок `##` воспринимайте как отдельный слайд.

## Слайд 1 — Титул

Курс: проектирование и разработка клиент-серверных приложений.  
Тема: программное обеспечение бронирования переговорных коворкинга («MeetingHub»).  
Авторское поле: ФИО, группа — заполните вручную перед защитой.

## Слайд 2 — Целеполагание

**Цель:** снизить количество ручных согласований переговорных, автоматически блокировать временные столкновения и обеспечить прозрачное разделение действий между посетителем и персоналом площадки.  
**Критерии успеха:** SLA на ответ API быстрый локально, ошибки конфликта возвращают осмысленные HTTP коды (`409`), данные авторизации воспроизводимы в Docker Compose.

## Слайд 3 — Анализ предметной области

Стейкхолдеры:

- Посетитель (бронирует слот без административного маршрута),
- менеджер офисной инфраструктуры,
- технический администратор платформы.

Выявлены сущности `User/Room/Booking`, правила временного плана, ограничения по ролям, требование логической изоляции чужих журналов. Поддержание консистентности реализовано транзакциями приложения через Prisma без ручного SQL.

Подробнее: `docs/01-domain-analysis.md`.

## Слайд 4 — Проектирование

**Архитектура клиент-сервер:** браузер (SPA) общается с REST API по JSON, на стороне сервера включён доменный слой + guard-цепочка NestJS для RBAC/JWT.

**Модели**

- Структурный анализ IDEF0 (уровень A0, декомпозиции A1) — см. `docs/02-diagrams.md`.
- Прецеденты, состояние бронирования, последовательность POST `/bookings`.
- ER-диаграмма и deployment map с фактической связкой SPA ↔ Nginx ↔ API ↔ Postgres.

## Слайд 5 — Реализация клиента

Стек UI: React 19 + Vite 8 + React Router для маршрутизации.  
Реализованы экраны маркетинга входа (`/`), аутентификация, список переговорных с формами для управляющих ролей, журнал бронирований со статусами и подтверждением PATCH эндойнета.

Клиент общается с относительными путями (в dev режиме — прокси Vite), а в Docker — статика обслуживается Nginx, который отправляет только API в контейнер `api`.

## Слайд 6 — Реализация сервера

Стек NestJS modular monolith (`Auth/Users/Rooms/Bookings`).  
Подключены `ConfigModule`, Prisma клиент lifecycle hooks, bcrypt для паролей, глобальные pipes валидации.  
Строго отделённые сценарии ролевого доступа: отдельные guard’ы `@Roles()`, отдельные эндойнты `PATCH .../confirm` для узких привилегий MANAGER.

## Слайд 7 — Тестирование

**Юниты и свойства качества домена:**

- Изолированные тесты с мок-прусманом моделируют сценарии RBAC (`RolesGuard`, JwtStrategy против реальной БД записи).
- `npm run test:phase` — фазированный прогон без тяжёлых свойств fuzz.
- `npm run test:fuzz` использует fast-check для генерации тысячи произвольных DTO домена без «немых» исключений.
- Контракт качества покрывается через `npm run test:cov` со 100 % ключевых метрик исходного кода приложения без декораторных `.module.ts` (чисто технические Nest-обёртки).

## Слайд 8 — Документирование и DevOps

- Репозиторий GitHub активен множеством гранулярных коммитов (сообщение + небольшой дифф).
- `Dockerfile` в backend описывает build + runtime с миграцией и автосидингом для демо.
- Frontend контейнер с `nginx.conf` смешивает статику SPA и проброс REST.
- `README.md` описывает структуру, команды локального запуска, фазы тестов, облачный rollout.

Облако: см. блок «Публикация в облако» readme — указаны параметры конфигурирования `DATABASE_URL` и `JWT_SECRET`.

## Слайд 9 — Выводы

Полностью воспроизводимое клиент-серверное приложение успешно демонстрирует:

1. Проработку анализа и архитектурных диаграмм уровня ВКР.
2. Серверную бизнес-логику с разграничением прав и противодействием «сломанным» данным через валидацию + fuzz.
3. Удобный пользовательский интерфейс, интегрированный в Docker стенд без ручной настройки SPA прокси.
4. Осознанную стратегию тестового покрытия и активную историю версий под требование GitHub активности.

**Рекомендации следующей итерации:** добавить refresh-токены, webhook уведомлений календаря, интеграцию с платёжными шлюзами для платных локаций, observability трассировки.
