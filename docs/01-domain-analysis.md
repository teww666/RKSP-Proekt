## 1. Назначение системы

`MeetingHub` автоматизирует цикл управления ресурсами коворкинга: наличие переговорных комнат, их характеристики, журнал занятости и управление статусами бронирований. Пользователями выступают посетители коворкинга, офисные менеджеры и администраторы площадки.

Ключевая задача продукта — предотвращение столкновений по временному интервалу, прозрачное разделение доступа между ролями и быстрая синхронизация данных между фронтенд SPA и базой Postgres.

## 2. Основные сущности

| Сущность | Назначение |
| --------- | ----------- |
| `User` | Учётная запись посетителя или сотрудника. Роль задаёт ограничения API. Пароли хранятся исключительно в виде `bcrypt`-хеша. |
| `Room` | Описание физической переговорной: вместимость, инвентарь, локализация, флаг активности для скрытия из выдачи. |
| `Booking` | Связка пользователя и комнаты с интервалами `startAt`/`endAt` и машиной состояния `PENDING → CONFIRMED → CANCELLED`. |

Целостность бронирований обеспечивается ограничениями приложения на пересечения и каскадным удалением при необходимости административных операций.

## 3. Роли и зоны ответственности RBAC

- `USER`: самостоятельное создание записей только на своё имя, отмена активных записей для себя, просмотр только собственной истории.
- `MANAGER`: полный журнал аудита клиент-серверной логики, подтверждение статусов, создание новых описаний переговорных, выключение/включение площадок.
- `ADMIN`: включает привилегии MANAGER плюс жёсткие операции (удаление комнасы вместе с зависимыми данными через каскад).

Никакое поле DTO регистрации не позволит подняться выше USER — эскалация контролируется серверным кодом, а каждый запрос переоценивает данные против актуальных записей в БД после декодирования JWT.

## 4. Правила временного планирования

1. `endAt` строго больше `startAt`; при обновлении пересматривается оба времени безопасными преобразованиями `Date`.
2. При роли `USER` запрещается отправлять прошлые интервалы, что защищает от простейших ошибок календаря и намеренного «накручивания» истории административной отчётности.
3. Любой новый временной промежуток проверяется на пересечение с уже существующими `PENDING/CONFIRMED` записями той же комнаты (`assertNoOverlap`).

## 5. Интеграции и граничные режимы

- Публичные эндпоинты: `POST /auth/login`, `POST /auth/register`, `GET /health`.
- После авторизации все маршруты обёрнуты `JwtAuthGuard`, а выборочно применён `RolesGuard` для мутаций.
- Сервер включает `ValidationPipe`, что отражает методику защиты от «грязных» payload: любые случайные и мусорные поля режутся фильтром `forbidNonWhitelisted`.

Подробнее визуализация см. в документе `docs/02-diagrams.md` (UML, последовательности, архитектурное распределение).
